quarkus-smithy: customer experience report

What changes for a developer building a Quarkus app on top of a Smithy model.

The quarkus-smithy extension exists to make Smithy-Java feel native to a Quarkus application — codegen runs as part of quarkusGenerateCode instead of a separate Gradle plugin, and Smithy Server beans participate in the standard Quarkus startup/shutdown lifecycle. This report sketches the before/after experience for the three programming models the extension supports.

The three programming models

Model modes in smithy-build.json What's generated What ships at runtime
Server-bean ["server"] CoffeeShop service stub, *Operation interfaces, model classes Server bean (Smithy Netty), managed by the lifecycle observer
Typed-client ["client"] CoffeeShopClient, model classes CDI-injected client; no Smithy server
Types-only ["types"] Model classes only (POJOs) User-driven dispatch (Vert.x route, JAX-RS, …); no Smithy server, no Smithy client
Same code, different framing. The extension's CodeGenProvider is mode-agnostic — whatever modes the user puts in smithy-build.json is what gets emitted. The lifecycle observer only does work when a Server bean exists, so Typed-client and Types-only apps pay nothing extra at runtime.

Before / after: build.gradle.kts

This is the most concrete artifact. Without the extension, a Quarkus user building on Smithy-Java applies the smithy-base Gradle plugin, declares smithyBuild(...) dependencies, and wires generated sources into the source set themselves. With the extension, the entire build-side surface is one implementation dep.

Before — Quarkus + Smithy via smithy-base

plugins {
    `java-library`
    id("io.quarkus") version "3.35.3"
    id("software.amazon.smithy.gradle.smithy-base")
}

dependencies {
    smithyBuild("software.amazon.smithy.java:codegen-plugin:$smithyJavaVersion")
    smithyBuild("software.amazon.smithy.java:server-api:$smithyJavaVersion")

    implementation("software.amazon.smithy.java:server-netty:$smithyJavaVersion")
    implementation("software.amazon.smithy.java:aws-server-restjson:$smithyJavaVersion")
}

afterEvaluate {
    val codegenPath = smithy.getPluginProjectionPath(
        smithy.sourceProjection.get(), "java-codegen").get()
    sourceSets {
        main {
            java { srcDir("$codegenPath/java") }
            resources { srcDir("$codegenPath/resources") }
        }
    }
}

tasks {
    val smithyBuild by getting
    compileJava { dependsOn(smithyBuild) }
}

After — Quarkus + Smithy via quarkus-smithy

plugins {
    `java-library`
    id("io.quarkus") version "3.35.3"
}

dependencies {
    implementation("software.amazon.smithy.java:quarkus-smithy:$smithyJavaVersion")

    implementation("software.amazon.smithy.java:server-netty:$smithyJavaVersion")
    implementation("software.amazon.smithy.java:aws-server-restjson:$smithyJavaVersion")
}

// .smithy files live under src/main/smithy/ — picked up automatically.
// No source-set wiring. No compileJava.dependsOn. No smithyBuild config.

Before / after: server lifecycle

Without the extension, the user runs Server.start() from main() and parks the thread. With the extension, the user produces a Server bean; Quarkus's lifecycle owns startup and shutdown.

Before — BasicServerExample.java

public class BasicServerExample implements Runnable {
    static final URI endpoint = URI.create("http://localhost:8888");

    public static void main(String[] args) {
        new BasicServerExample().run();
    }

    @Override public void run() {
        Server server = Server.builder()
                .endpoints(endpoint)
                .addService(CoffeeShop.builder()
                        .addCreateOrderOperation(new CreateOrder())
                        .addGetMenuOperation(new GetMenu())
                        .addGetOrderOperation(new GetOrder())
                        .build())
                .build();
        server.start();
        try {
            Thread.currentThread().join();
        } catch (InterruptedException e) {
            try { server.shutdown().get(); }
            catch (InterruptedException | ExecutionException ex) {
                throw new RuntimeException(ex);
            }
        }
    }
}

After — CoffeeShopServerConfig.java

@ApplicationScoped
public class CoffeeShopServerConfig {

    @Produces
    @Singleton
    Server server() {
        return Server.builder()
                .endpoints(URI.create("http://localhost:8888"))
                .addService(CoffeeShop.builder()
                        .addCreateOrderOperation(new CreateOrder())
                        .addGetMenuOperation(new GetMenu())
                        .addGetOrderOperation(new GetOrder())
                        .build())
                .build();
    }
}

// SmithyServerLifecycle (provided by the extension) calls
// server.start() on StartupEvent and server.shutdown().get()
// on ShutdownEvent — for every Server bean it finds.

The producer-method body is byte-identical to the upstream BasicServerExample.run(). The only Quarkus-specific surface a user has to learn is the @Produces wrapper. Everything else — port binding, graceful shutdown, draining the listener — is inherited from Quarkus's standard lifecycle plus the extension's 30-line observer bean.

Per-model walkthrough

Server-bean — full Smithy server inside Quarkus

Generated CoffeeShop service + *Operation interfaces. User produces a fully-built Server bean; the extension's lifecycle observer starts the Smithy Netty listener on StartupEvent and drains it on ShutdownEvent.

  • What ships: quarkus-smithy, server-netty, aws-server-restjson (or another protocol).
  • Two listeners run side by side: Smithy on :8888, Quarkus's Vert.x on :8080.
  • End-to-end verified: curl :8888/menu returns the static menu; PUT :8888/order writes through the generated CreateOrderOperation impl; GET :8888/order/{id} reads back.

Typed-client — call an upstream Smithy service

Generated CoffeeShopClient exposed via a @Produces method. No Server bean. The extension's lifecycle observer finds zero servers and no-ops silently.

  • What ships: quarkus-smithy, client-core, aws-client-restjson (or another protocol).
  • Endpoint config via standard CDI: @ConfigProperty(name = "coffee-shop.upstream-endpoint", defaultValue = "http://localhost:8888") — overridable per environment without code changes.
  • End-to-end verified: the example proxies :8081/menu → upstream :8888/menu via the typed client, with PUT and GET /order/{id} round-tripping correctly.

Types-only — Smithy as the DTO source of truth

Just generated POJOs (Menu, MenuItem). User dispatches them however they want — typically a Vert.x route or a JAX-RS resource using JsonCodec for serdes.

  • What ships: quarkus-smithy, core, plus a codec module if needed.
  • Lifecycle observer is silent: no Server bean exists; the extension contributes only codegen.
  • Recommended scoping: "selector": "[id|namespace = 'com.example']" in smithy-build.json, so generated output stays pinned to your namespace even if trait jars enter the classpath.
  • End-to-end verified: GET :8080/menu returns the static menu encoded by Smithy's JsonCodec; POST :8080/menu/echo deserializes a posted Menu and round-trips it back.

What the extension is, in one paragraph

Build-time, the extension provides a CodeGenProvider that runs JavaCodegenPlugin in-process during quarkusGenerateCode and drops the output into Quarkus's build/classes/java/quarkus-generated-sources/smithy/ directory, which compileJava picks up automatically. Runtime, it provides a 30-line CDI bean (SmithyServerLifecycle) that observes StartupEvent and ShutdownEvent and starts/shuts down every Server bean it finds via Instance<Server>. That's it.

What it's not

  • Not a code generator. The actual Smithy-Java codegen (JavaCodegenPlugin) is unchanged; the extension just calls it from Quarkus's build hooks.
  • Not a runtime framework. Generated code is identical whether you use this extension or smithy-base. Switching does not change wire behavior.
  • Not opinionated about transports. Server-bean apps still own their own Netty listener on a separate port. A unified-server mode (Smithy operations dispatched from Quarkus's Vert.x router) is named in CONTEXT.md as deferred future work.
  • Not a dependency injection layer for operations. Operation impls are wired in user code via the generated builder; no @SmithyService annotation discovery.
